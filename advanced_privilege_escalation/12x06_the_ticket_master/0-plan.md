To evaluate the path to Thornbury’s database server through the domain's identity infrastructure, this engagement plan establishes an objective, metrics-driven authorization assessment framework.

## Material Utility and Non-Plaintext Authorization Assessment
Recovered authentication material has a strictly defined use centered on an explicit pre-use verification process. Before initiating an administrative session on Thornbury’s objective database server, we follow a strict sequential validation flow: first, we verify the identity relationship by confirming that the material maps to a specific domain user, group membership, or authorization path; second, we confirm access entitlement by validating these attributes against active domain roles and access control lists; only after these verification steps are completed will we use the recovered material to establish the administrative session. For captured material where a plaintext password is not recovered, this same mandatory identity-to-access validation sequence is applied to ensure its authorization utility before any administrative use.

## Cracking Evaluation and Resource Thresholds
We execute a selective cracking strategy where each recovered hash is subjected to an explicit cost-benefit test before any cracking time is allocated. Material is prioritized based on a calculated ratio where the identity’s probable path to Thornbury's database server represents the expected value, and the password entropy represents the expected effort. We only crack material when the likelihood of gaining direct database access outweighs the estimated cracking time. A hash is skipped entirely if its access value is low while its estimated cracking effort is high. We continuously reassess cracking effort against remaining engagement hours, stopping or reprioritizing our focus to mitigate diminishing returns whenever the expected access value no longer justifies the ongoing resource allocation.

## Domain Controller Records and Analytical Scope
We anticipate that prior to any active assessment step, the Domain Controller records standard telemetry through Kerberos Authentication Service and Ticket Granting Service event logging, specifically tracking Event IDs 4768 and 4769. The client’s Security Operations Center will reconstruct our engagement from these exact artifacts. To maintain a non-disruptive, controlled scope, a strict constraint is established: we will not interact with or target the Domain Controller itself. The entire objective remains framed strictly as an identity relationship problem, focusing on how authorization paths are structured within the domain.
