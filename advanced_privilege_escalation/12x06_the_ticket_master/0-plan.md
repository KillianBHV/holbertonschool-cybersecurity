# Engagement Plan
To reach Thornbury’s database server via identity paths rather than system exploitation, we enforce a comprehensive, identity-first verification framework to systematically evaluate all recovered authentication material.

## Identity Verification and Non-Plaintext Authentication Flow
Recovered cryptographic material has a strictly defined use centered on evaluating direct authentication viability before any parsing, processing, or cracking operations are initiated. Upon initial collection, we validate the recovered identity against domain groups, nested roles, effective permissions, Access Control Lists (ACLs), and Active Directory delegation paths to map its explicit security relationship to Thornbury's target database server. If this validation flow confirms effective administrative rights over the target infrastructure, the material is utilized directly via Pass-the-Hash (PtH) or Pass-the-Ticket (PtT) techniques to establish an authorized administrative session. Plaintext recovery is treated as secondary; we only evaluate if the material itself supports an authorized authentication path. This ensures that no unnecessary actions are performed if the collected asset already provides the required administrative access to the actuarial platform.

## Cracking Priority Rubric and Stopping Rule
Cracking is executed only as a last resort when direct non-plaintext authentication paths are entirely unavailable. We score remaining hashes by strictly weighing expected access value against total cracking effort. Expected value depends on the identity’s proximity to Thornbury’s database server, while effort is estimated by password entropy, cryptographic algorithm strength, and dictionary complexity. We explicitly skip hashes whose computed time cost outweighs their access value. Our strict stopping rule dictates that cracking ceases immediately if a hash's time-to-crack estimate exceeds 45 minutes, or if a lower-cost identity path providing equivalent database access is discovered during continuous path re-evaluation.

## Domain Controller Records and Constraints
We anticipate that before we perform any active movement, the Domain Controller will record our presence through Kerberos Authentication Service and Ticket Granting Service logs, specifically tracking Event IDs 4768 and 4769. The client’s internal Security Operations Center (SOC) will attempt to reconstruct our engagement from these exact logged artifacts. To guarantee absolute safety and avoid production disruption, we establish a hard constraint: we will not touch or target the Domain Controller. The entire objective remains framed as an identity path problem, focusing solely on who the domain thinks we are.
