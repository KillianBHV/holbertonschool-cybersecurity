# Engagement Plan
To evaluate the path to Thornbury’s database server through the domain's architecture of identity, this plan establishes a neutral authorization assessment framework.

Material Utility and Non-Plaintext Authorization Assessment
Recovered authentication material has a defined use centered on verifying its intrinsic authorization utility. For captured material where a plaintext password is not recovered, its utility is determined by assessing whether the cryptographic asset independently supports a valid, authorized authentication path. We analyze the material to see if the identity's existing domain groups, roles, and delegation paths possess legitimate relationship alignment with the target database server. Non-plaintext assets, such as hashes or tickets, are evaluated to confirm if they provide sufficient cryptographic validation to map a path, rendering plaintext translation unnecessary for verifying authorization status.

Cracking Evaluation and Resource Thresholds
Cracking is treated as a secondary analysis metric, applicable only when non-plaintext material lacks sufficient structural data to determine path utility. We prioritize the evaluation of remaining cryptographic material by weighing its potential access value against processing cost. The value is defined by the identity’s structural proximity to Thornbury’s database server, while the cost is estimated by password entropy and algorithm complexity. A strict stopping rule dictates that verification processing ceases if the resource cost outweighs the analytical value, or if a lower-cost identity relationship providing equivalent mapping data is identified.

Domain Controller Records and Analytical Scope
We anticipate that prior to any active assessment step, the Domain Controller records standard telemetry through Kerberos Authentication Service and Ticket Granting Service event logging, specifically tracking Event IDs 4768 and 4769. To maintain a non-disruptive, controlled scope, a strict constraint is established: we will not interact with or target the Domain Controller itself. The entire objective remains framed strictly as an identity relationship problem, focusing on how authorization paths are structured within the domain.
